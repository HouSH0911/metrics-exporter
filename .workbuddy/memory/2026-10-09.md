### 关键结论（供后续会话复用）
- 当前版本 v1.6，源码文件命名带版本后缀：`main_v1.6.go` / `struct_v1.6.go` / `sup_func_v1.6.go` / `json_handle_v1.6.go` / `install_service_v1.6.go`。历史版本归档在 `bak/v0.1 ~ bak/v1.5`。
- 目标运行环境是 Linux（CentOS 6/7+），部署为 systemd 或 SysVinit 服务，监听端口由 config.json 的 `port` 字段配置（默认 9600）。
- 两个端点：`/check` 返回 JSON（v0.1 起，向后兼容），`/metrics` 返回 Prometheus text 格式（v1.5 新增设计，v1.6 落地）。
- CLAUDE.md 已过时：仍写着 `metrics-v1.4.go` / `service.go` 的构建命令，且未提及 `/metrics`、`allowedHosts`、`instance`、`recentMinutes` 等。如需修改需同步更新。
- 发现的潜在问题（未修改，仅记录）：
  1. Prometheus 输出中目录/文件/进程/端口指标恒为 `1`，状态放在 `status` 标签里，不符合 Prometheus 惯例（应为 0/1 表示实际状态，用标签区分会造成 series 数量翻倍且无法直接告警）。
  2. `writePrometheusMetrics` 在循环内部重复写 `# HELP` / `# TYPE`，会产生重复元数据行，严格解析器可能报错。
  3. `doCollectMetrics` 中 `cache.processScanAt` 在 RLock/Lock 之外被直接读取（第 138 行 `now.Sub(cache.processScanAt)`），与写操作存在 data race，`go test -race` 可复现。
  4. `checkPort` 在每次 HTTP 请求时同步执行（最多 5s 超时 × 端口数），未做缓存；`handler` 和 `metricsHandler` 存在约 80% 重复的采集逻辑。
  5. `main` 里 `handler(w, r, config)` 直接传值拷贝全局 config，未加 `configMutex.RLock()`，存在竞态。
  6. 时区硬编码 `Asia/Shanghai`（collectCallTypeStats），容器无 tzdata 时 `LoadLocation` 会失败并被忽略。
